# The frontend (`mira-gui`)

`mira-gui` is a Qt6 client of the REST API in [`api.md`](api.md). It never links against `mira_core`.

## UX principles

These hold across every screen; a new one follows them without being told.

- **Nothing moves on its own.** A control that comes and goes keeps its space while hidden (`setRetainSizeWhenHidden`), so revealing it never shifts a row, a header or a card. A header is the same height with or without its buttons.
- **No permanent help chrome.** Help lives on the thing it explains: a setting's doc is its label's tooltip after 0.3 s of hover, not a [?] icon. Labels say what the control does, so most never need the tooltip.
- **Undo before reset.** A changed value shows a dot and an undo button that stay until it's saved or undone; undo puts back the saved value. Reset to defaults is a card-level action, offered only where the card's values belong together (layout, shortcuts, detection, scanning and the like) and only while something in it isn't default. Neither applies before Save.
- **Line up with the structure.** Popups anchored to a card start at the card's left edge (6 px in) rather than centering under whatever was hovered.
- **Every interactive state is styled.** No Fusion bevels or native hovers: frameless icon buttons share one flat rounded hover (`QToolButton[autoRaise="true"]` in `base.qss`), and a new button kind gets its hover, pressed and checked looks together. Focus has one look everywhere, the focus ring, so no widget or stylesheet draws its own beyond a field's accent border while typing in it.
- **Previews are never blank.** With no games to show, a preview draws sample cards in the theme's own colors (`theme::SampleArt`), so the setting still shows what it changes.
- **Quiet by default.** Secondary actions are muted text or icons until hovered; nothing explains itself in a subtitle or hint line.

## Windows

`mira-gui` opens on the **grid** (`window/LibraryWindow`): cover tiles, a left sidebar and a custom top bar (`window/TopBar`) in place of a native titlebar. The window is frameless. The top bar carries the Mira badge and name; dragging its empty area moves the window, double-clicking the top bar toggles maximize, and the edges resize. Moves and resizes go through `QWindow::startSystemMove`/`startSystemResize` so they work on Wayland and X11.

### Library page

The grid page (`library/LibraryPage`) opens on the same tab row as a source page (`components/TabRow`): tabs for All, Games, Apps, Installed and Not installed (Playing now, Needs attention, Never played and the rest are in the filter menu only), then the filter and sort menu (`library/FilterSortPill`) and the search box. When the window narrows, the search box gives way first (320 px down to 160, then a search button that opens it again, as does Ctrl+F), then the last tabs move into a More menu; the current tab always stays, and source pages' rows do the same. There's no page title; the sidebar says where you are. Under them, *Continue playing* (`library/ContinueRow`) shows large cards for running and recently played games while the whole library is shown. A game that isn't running but has a tool open that it started (a mod manager, mirad's `tools`) counts as running there and in the sidebar's recently played rows, its status line reads *Vortex open*, and its menu has *Close Vortex*, which stops the game's tools. Tiles show a status line, which also names the source a game came from: after the status ("Playing · Steam"), or alone and muted when there is none. The search box matches names and tags (a plain word finds either, `#word` only tags), and the filter menu's Tags section lists every user tag as a pill with its count under the current filter, in the library's tag order, two to a row with equal widths (the popover widens up to 360 px to fit the names, then cuts them short); picked tags all have to match, show after the filter's name on the pill, and never bring hidden games outside hidden mode. A middle click on the pill, or a click on the sidebar's Library while the library is already shown, goes back to all games with no tags picked and an empty search. A tag chip's menu in a game's card has *Show games tagged …*. A game that isn't set up has a dimmed cover with a *Not set up* badge over its name, and is listed under Needs attention; playing it opens its setup card. *Detect again* beside the Executable field (installed games) rebuilds the field's list from the game's folder. Each part can be turned off in Settings → Interface.

### Hidden mode

Ctrl+H (or *Hidden games* in the filter menu) turns hidden mode on or off on any page. `GameLibraryModel::ShowingHidden` holds it, so every view follows: the grid and its filters, counts and Continue playing, the not-installed titles, source pages (their grids, counts and Not installed sections), the sidebar's pinned and recently played rows and its source counts and covers, the Tags page's counts and picker, and the Runners page's "Used by" counts. Outside it none of these list a hidden game; in it they list only hidden ones. The theme swaps its accent for `accent_hidden` (purple by default), tints the top bar with it, and the bar's middle says which key leaves. It isn't kept across restarts, and big screen never lists hidden games. The sidebar's sources in hidden mode mirror the normal list until *Hide from sidebar* or a source's *In sidebar* switch is used in hidden mode. That gives hidden mode a list of its own (`in_hidden_sidebar`), which the normal list's changes leave alone from then on. In hidden mode the Sources page's *Same sidebar sources as outside hidden mode* switch shows which it is, and turning it on mirrors again.

A not-installed title's menu has *Hide* (or *Unhide* in hidden mode), through `POST /v1/library/hidden`; mirad tags the game `hidden` if the title is installed later, and keeps the title hidden when a hidden game is removed.

Settings › Library › Hidden games sets a password (`library/HiddenLock`'s `HiddenPasswordRow`, a form that opens under the row). While hidden games are locked, mirad leaves them out of everything it sends, so the GUI simply doesn't have them. Ctrl+H then opens `HiddenUnlockCard` over the content first, and hidden mode opens once the unlocked list has arrived. `hidden.changed` keeps the window in step: when hidden games lock (idle, `hidden.lock_on_leave`, another client) the window leaves hidden mode and lists games again, as do owned titles, source pages and the Tags page. Leaving hidden mode posts `/v1/hidden/left` and mirad decides whether that locks. Key presses, clicks and scrolling anywhere post `/v1/hidden/activity` at most once a minute while unlocked, and quitting locks.

### Sidebar

From top to bottom: the Mira header, the Library, Runners and Settings rows, pinned games, the sources, recently played games (off by default), then Add games with the Downloads button beside it, and the count of games shown with the Tags button under Downloads. Each of those two opens its page, and a second click goes back to the library.

*Add games* opens `library/AddGamesCard`, an in-window card (`components/WindowCards`) with four choices: *Scan library folders*, *Already installed* (a folder or a program, from Choose…'s menu), *Installer* and *From your app menu*. Steam, Lutris and Heroic aren't there, since their sources import them. A pick replaces the card's first page with its own, which has a back arrow; cancelling the file picker leaves the card as it was. Already installed shows the folder or program (Change…), the program that starts a folder (classify's `programs`, best first), the name, game or app (classify's guess) and *Move it into* the first Mira folder's Games or Applications, on unless it's already in a library folder; Add moves it first (`POST /v1/library/import`) when that's on, then adds it (`POST /v1/games/manual`). Installer adds the file as not set up and hands over to its setup card. From your app menu lists the entries mirad hasn't added (fetched as the card opens, so the first page shows their count), with a search field; ticking one shows its *App* chip, on when the entry isn't marked as a game, in a space kept while it's hidden. The footer counts the games and apps picked and *Add N* imports them in one `POST /v1/desktop-entries/import`. Dropping one file or folder on the window opens its page (its setup card for an installer, Already installed otherwise); several dropped at once are each moved in by mirad's guess, and one it can't place opens its page.

Pinning a game (game menu, or several at once from the batch menu, which offers Pin/Unpin and Hide/Unhide for whichever selected games each would change) adds the `favorite` tag, the same one Lutris imports its favorites under. Pinned games list by name under PINNED; their tiles carry no mark. PINNED follows hidden mode: hidden pinned games show only in it, and only they do. Clicking a pinned or recently played row plays the game; the second click of a double click is ignored, since the list can reorder under it. Source rows lead with up to three of the source's covers fanned like a hand of cards (most recently played on top; a dashed outline when it has none), then the name over a muted line: how many games it has, out of what the store owns once `OwnedTitles` has listed it ("2/229 games"), *No games*, or *Signed out* in orange for a store that has games but is signed out. When the source's store tool or emulator has a newer release (`GET /v1/updates`, asked at start, after each setup or install job, and when `updates.check` changes; not while it's off), the row's menu offers *Update butler (v15.32.0)*; the top bar's Updates panel is what announces it. With covers turned off, a row is one line with a colored dot and the count.

Only sources that are set up show in the sidebar. *Manage sources* (`sources/ManageSourcesCard`) is an in-window card over the content, sharing the sidebar style card's overlay so the sidebar stays bright beside it. It lists every source in sidebar order as one freely reorderable list (drag the grip or Alt+Up/Down), each row with its kind tag and status inline, a *Games in library* switch that keeps its games on or off the library page (they stay on the source's own page), Set up for one that isn't set up yet, and a ⋯ menu for open, import, show in sidebar and remove. Every change applies at once. `sources/Sources` lists them for every view.

### Source pages

Each source row opens `sources/SourcePage` in the grid's place:

- **Stores** (Epic Games, GOG, itch.io, Amazon Games, Humble Bundle): sign in (the helper tool downloads first), import installed games. Owned games that aren't installed show as a second grid with an Install button (Download for Humble). A downloaded Humble bundle's button becomes *Add to library…*, which opens the add-game dialog on its download folder; a bundle with nothing to download (such as a Steam key) says so.
- **Launchers** (Battle.net, Ubisoft Connect, EA app): install the launcher into its own prefix, open it, import its games.
- **On this computer** (Steam, Lutris, Heroic): import what the other program installed. Steam also lists owned games once a Web API key is set.
- **Local**: every game from no source at all (scanned from library folders, added by hand, desktop entries), with *Scan library folders* as its import. It can't be turned off or removed, has no settings and no Not installed section. `SourceIdOf` maps a game's `source` to the listed source it belongs to.

A mod manager's page lists the games it's on as tiles under "Games with Vortex" (a game's launch option with the manager's id counts it as one of its sources). *Add to games* opens `sources/ModManagerPicker` in the page's place: the Windows games it isn't on yet as covers to tick, hidden ones in their own section as on the Tags picker, with a search, Cancel (or Esc) and *Add to N games*, which starts one `POST /v1/games/{id}/mod-managers/{manager}` per game and reports on the page's status line once all have finished. Taking it off a game stays on the game's page, since that purges its mods.

A page is one scroll: a top row with the source's status and its Sign out / Open, Import, settings and ⋯ buttons, a "Set up <source>" card while the source isn't signed in or installed (`sources/SourceSetupCard`, holding `setup/SignInPanel` without its Back row, or `setup/OfficePanel` for Microsoft 365), the source's games as tiles (`library/TileGrid`) under "In your library", a divider, then "Not installed" with its count ("171 of 227" while filtered). Tiles on a source page don't name their source. A store's list is asked for as the page opens, without waiting for its status: mirad answers from the list it stored, so it shows at once. Only when mirad has to ask the store itself (the first time, or after signing out) does the section show, after 150 ms, a rail, "Asking <store>…" and three placeholder tiles. While mirad re-checks the store behind the shown list (`library.catalog_checking`/`checked`) a faint rail runs under the heading, and a changed list is fetched again. Refresh asks the store now (`fresh=1`). Above the tiles, `library/RatingChips` filters by ProtonDB tier and by Steam's review label (the four negative ones grouped, too few reviews as "Not rated"), each chip with its count and in its own color (ProtonDB's medal colors, Steam's review colors): chips in a row add up, the two rows narrow each other, and "Clear filters" undoes them. Tiles show the ProtonDB pill and "NN% positive"; ratings that arrive with a cover update the chips' counts. The zoom slider sizes each page on its own unless `tile_size_synced` is on. Covers for games that aren't installed come from `/v1/library/artwork`. Login URLs and paste parsing come from `mirad`, so the page only holds wording. A source whose *Games in library* switch (Sources page) is off still lists its games here; only the library page and its Continue playing row leave them out. Hovering a not-installed title asks mirad for its size (`GET /v1/library/size`), once per title while the page lives (a store mirad can't size isn't asked again); the hover card then shows *9.1 GB on disk · 4.5 GB download* under its status, also while the title is installing.

`setup/SignInPanel` puts numbered steps beside a drawing of the page the user will land on (`setup/BrowserSketch`, in the theme's colors, the thing to copy outlined), or under it in a narrow window, with the wording per source in `setup/SignInGuide`. It asks mirad where things stand only once it's first shown, so a panel made ahead starts nothing. A store's helper tool downloads first ("Getting ready…"); once its page is opened, every clipboard change (and the window becoming active again, which is when Wayland hands it over) goes to `POST /v1/stores/{id}/login/find`, and a credential mirad recognises signs in by itself and is cleared from the clipboard; the paste field is the fallback. Steam's owned games take a key with the account picked from Steam's own sign-ins; a launcher installs (its log's last lines under the steps), then opens to sign in inside it. Signing in or installing sets the source up (`added`, `PATCH /v1/sources/{id}`). Microsoft 365 uses `setup/OfficePanel` instead: the plan, the install, then the picked apps one at a time.

The banner's gear opens `sources/SourceSettingsCard` under it: the source's runner (`/v1/sources/{id}/runner`) and every schema setting under its own keys (`<id>.*`, plus `launchers.<id>.*`), in the same rows as Settings and saved or discarded together from the card's foot. The banner's ⋯ menu updates a store's tool, opens a launcher's prefix tools (folder, winetricks, run a program, log) and removes the source through the same confirmation Manage sources uses.

### Set up Mira

First launch (a `frontend.toml` with neither `onboarded` nor a saved window size) shows `setup/SetupWindow` instead of the main window, and sets `onboarded` at once so it opens on its own only once; the main window (or big screen) opens when it closes. It's a fixed-size window of pages with Back, Skip and Next in its footer and dots for where you are, which follow the picks as they're made. Every page can be skipped: *Skip setup* on the first page goes straight to the last, and skipping a page that picks things (what for, stores, applications) drops the pages its picks would have added (`setup/SetupFlow`, tested). The window is as tall as its tallest page, measured once over every page, so it never resizes.

Slow work starts only when a page is left with Next, never on Skip, and belongs to `setup/SetupWork`, owned by the main window, so it carries on after the window closes; a pill at the top right says what's under way. The pages:

- **Welcome**: three example heroes with Mira's name, what Mira does, where Mira keeps games (a pick sets `library_roots`, `prefix_root` and each store's install folder under it; a library folder that already holds games stays; NTFS, exFAT and FAT flagged), and, only when system packages are missing (`GET /v1/system/packages`), a note that Next asks for the password once, with *Choose packages* to untick some. Next installs them through `system::InstallPackages` and downloads the newest Proton when there's no Proton or Wine build.
- **What for**: Games and Windows applications, each a card; they decide the pages that follow.
- **Found on this computer** (games): Steam's installed games with their covers (`GET /v1/steam/installed`, nothing added yet) and a switch to add them, the account to read them for when Steam has several (`GET /v1/steam/accounts`), Lutris and Heroic each with a switch, and chips for the Proton and Wine builds, GameMode and Vulkan. Next saves the account and imports what's switched on.
- **Stores** (games): Steam, Epic, GOG, Amazon, itch.io and Humble as tiles, the first three picked. Next fetches each picked store's helper tool.
- **Applications**: Microsoft 365, and whether apps show under All and in big screen. Next starts Office's Windows setup (`POST /v1/launchers/office/install`, after `winetricks`).
- **A sign-in page per picked store**, "Store n of m": `setup/SignInPanel` with the drawing under the steps. Signing in refreshes the sidebar's sources and moves on by itself after a moment; the credential is gone from the clipboard by then, so the next store's page can't sign in with it.
- **Microsoft 365**: the plan (`launchers.office.plan`) and which apps (Word, Excel and PowerPoint ticked). Next asks for the apps (`POST /v1/launchers/office/apps`), which mirad adds once Office's own setup is done.
- **Look**: theme, corners and spacing presets over the shape overrides, and what tiles show, over a small library drawn with them; with only applications picked, the switches and preview are about apps. Changes apply as they're made.
- **Sidebar**: how pinned and recently played games draw, beside a sidebar drawn that way; recently played starts at three. With only applications picked, only pinned apps.
- **Done**: what was set up and what's left (and where to do it), *Start Mira when I log in*, *Open Mira in big screen* when the screen looks like a Steam Deck (1280×800) or a TV (over 40 inches), and a link to star the project on GitHub. *Open Mira* turns off every source that wasn't picked and has no games yet (`<id>.enabled`), unless setup was skipped as a whole.

Previews use the user's own games, most recently played first, and until there are any, three example games whose covers and heroes are fetched from Steam's CDN into memory only (`DemoArt`).

### Runners page

`runners/RunnersPage` has a Proton/Wine switch that filters both of its lists. They are settings cards in two columns, which stack into one on a window under 1150 px wide:

- **Installed** builds are one row each: the label, a Default tag on `default_runner.windows`, and how many games use it, its version and source inline (elided when narrow). Builds Mira downloaded show Update when there's a newer one and Remove in their ⋯ menu; distro and Steam builds show as managed outside Mira. After an update it offers to remove the old build. *Make default* (⋯) and *Pick automatically instead* (the note under the card) set `default_runner.windows`.
- **Get more** lists releases from the chosen source (the dropdown in its header), with date, size and checksum inline and an Install button on each.

A Missing tools card above Installed offers to install umu-launcher or winetricks when either is missing.

### Tags page

The sidebar's *Tags* row (between Runners and Settings) opens `tags/TagsPage`, settings cards from `GET /v1/tags` and the `tags.*` settings. Like Settings, it's built on each open, off screen, and shows once its tags and settings are in (`TagsPage::Ready`), replacing the page it leaves only then; going elsewhere meanwhile drops it, and a failed load says so and stays where it was. Leaving it deletes it, closing an open picker unapplied and dropping a question in its bar. Steam is asked for missing tags only once a session, whichever page asks. Your tags and Tag settings share a left column only a little wider than their rows need; Tag settings sits at the bottom and Your tags takes all the height above it (at least 240 px), its rows scrolling inside with GAMES and FOLDER column headings pinned over them, so Tag settings is always in view. From Steam fills the rest, its rows in as many equal columns of at least 250 px as fit (`RowColumns`), read across, names cut short with an ellipsis; below 1000 px it goes under the left column. Each row's count is an accent pill, stronger the more games have the tag (log scale from two games to the most). A round plus button opens the picker, filling with the accent while its row is under the pointer. Rows are kept and updated in place as the tags change, so a switch flipped or a count changed never rebuilds the page; a From Steam row exists only while it shows (most of Steam's tags are on one game and start hidden), and the picker lets go of its covers when it closes, so a restyle polishes only what's in view. Esc in the picker goes back, through the window's Esc chain.

- **Your tags**: folder tags first, in `tags.folders` order, which picks the folder of a game with several; their grips drag them into another order (or Alt+Up/Down), asked about in the change bar when that moves folders. Then the other tags, most games first. Each row has its count, a Folder switch, which makes it a folder tag in every library folder sorted by tag, and a ⋯ menu (*Choose games…*, *Rename…* in place, *Remove from every game…*). A rename asks in the change bar when it moves folders, and always before a merge into a tag the library already has. *New tag* in the header.
- **From Steam**: the Steam tags on two or more of the library's games that aren't its tags, most games first, with a search and a plus button on each. The tags on one game each (most of Steam's) show only from a button under the list or by searching. Steam tags never show anywhere else. Games whose metadata predates Steam tags get them once a session, when the page is built (`POST /v1/tags/fetch`).
- **Tag settings**: a switch per library folder for sorting it by tag, and where tags come from.

Adding, *New tag* and *Choose games…* open `tags/TagPicker` (a `library/GamePicker`, the cover picker it shares with mod managers' pages) in place of the cards: covers to tick, the games Steam gives the tag (or the games that have it) first and ticked, then every other game unticked, with a search, and a floating bar with an *Also a folder* switch, Cancel and *Add to N games*. The covers follow the library's tile size and zoom with it (Ctrl+wheel, the slider, Ctrl+=/-). Hidden games wait in a last *Hidden* section, the only one hidden mode shows, ticked only if they have the tag; store launchers aren't offered and keep the tag as they had it. It sends `POST /v1/tags/set`, so afterwards exactly the ticked games (and those launchers) have the tag. A change that moves folders (the Folder switch, sorting a library folder) asks in the change bar first with how many move (`POST /v1/tags/preview`), and applies at once when none would; removing a tag asks there too.

### Updates

The top bar shows `Update` only when Mira itself has a new version, and one click starts it (`updates/MiraUpdater`): it confirms if a game or install is running, downloads, installs through the system's own password prompt where a package needs it, closes games, stops mirad and restarts. The icon beside Activity opens `updates/UpdatesPanel`, which lists what `updates/UpdateChecker` found, grouped by `updates/UpdateRows`, each with its own Update button.

### Activity

Add games has *Download from links*: one paste is one game. It first offers to install aria2 and 7-Zip if they're missing (`system::EnsurePackages`), then `POST /v1/downloads/check` reads the links. The one page takes the links, and optionally a name (guessed from the download's file name otherwise), a password and, with more than one Mira folder, which one; Enter starts it and the Downloads page opens. `downloads/LinkDownloads` holds the queue from `download.*` events and feeds `DownloadTracker` as `Kind::Link` rows. `activity/DownloadList` draws the tracker's rows for both the Activity popover (compact: progress and buttons stacked) and *All downloads*, `downloads/DownloadsPage`, a page of the window like Runners, opened from the button beside Add games. The page sorts every download and install into Needs you, Downloading and installing, Waiting and Finished, and adds what links need: a password box, Move ahead, Cancel, with each row's buttons side by side. Its gear opens Settings › Downloads, where the speed limit and how many at once live. Waiting is in the order the queue starts them. A row's fix (Settings, a runner) closes the page. Rows update in place and rebuild only when one changes state, so a password being typed survives.

The top bar has room for one notice, the most important now (`LibraryWindow::SyncUpdates`): Mira updating, then a download waiting for a password (`Password` or `Passwords: 2`, opening `downloads/PasswordPopup`), then a failed download (opening the Downloads window, which marks it seen), then `Update`. Skip in the popup stops the notice asking about that download until the GUI restarts; the Downloads window still takes its password.

The top bar's download button opens `activity/DownloadsPanel`, titled Activity. It lists everything `activity/DownloadTracker` has seen from the event stream: game installers, store installs and updates, Humble downloads, launcher installs, tool downloads, runner downloads and `mirad`'s jobs (scans, imports, moving and deleting games, removing a source). `mirad` replays recent events on connect, so work started before the GUI opened also shows. Game installers report bytes written, and with a guess at the installed size from Steam's requirements (`estimated_bytes`) a percentage and "1.2 GB of about 4 GB", which the installer card also shows ("about 4 GB installed"); Epic, GOG, Amazon and itch installs report percent, speed and time left (`library.install.progress`), and Epic, GOG and Amazon how much of the download has come ("1.2 GB of 4.5 GB"), also drawn on the title's tile in the library, on its source page and in search: the title, a rail (moving while no percentage is known), the percentage and time left, and the speed or bytes written under it (`DownloadTracker::TileProgressFor`); jobs with steps report how far along they are. A row's name is cut short to fit the panel's fixed width (the whole of it in its tooltip), and its status wraps. A finished install offers *Show*, which selects the game. A notification the desktop didn't take is a failed row too (see Notifications): its message wraps as the name, with its fix as a button, and the same message again moves its row to the top instead of adding one.

`game/GameSetupCard` asks what a new game is, over the library in the same overlay as Manage sources: the title it's identified as (*Change…* turns the card to a search of Steam's titles), its name, the program (*Browse…* picks another), whether that starts or installs it, and game or app. It opens on a live `game.added` with status `not_set_up`, when an installer finishes, from *Set up…*, and from playing such a game; closing it leaves the game *Not set up*. An installer adds *Install onto* (for one on a disc) and *Show the installer* / *Install quietly*; a failed setup shows why, with *Look again*. For an archive (`library.archive_found`) it asks the same before extracting, with a password row when none saved opens it, *Delete the archive afterwards*, *Another app is extracting it* and *Extract and add*; Activity lists an archive that waits, or that another app has. While Mira is hidden or minimized a system notification asks, and the card waits for the window.

When a launch answers `saves_conflict` (the game's saves changed here and in its store's cloud or on the user's remote since they were last in sync), `actions::Launch` asks the window, which is a `actions::SavesChooser`, before trying again with the choice in the launch body's `saves`. On the desktop that's `game/SavesConflictCard` in the same overlay: the cover, "Which saves should Celeste start with?", one choice for this computer's saves and one for the cloud's or the other computer's (focused), each with when they last changed and how many files, then a muted *Play without syncing* and *Cancel*. Big screen asks with a menu of the same three. Closing the card any other way cancels the launch. Out of sight, a notification asks first and its button opens the card. A conflict mirad finds after a session comes as a persistent notification whose *Open saves* button opens the game's Saves page; while a launch from this window is waiting on that game, the notification is left out, since the card already asks.

While mirad works on a game's saves (`game.saves_activity`: a backup, a restore or a sync, including the stretch after a session from its exit through the upload), its tile draws an install's moving rail with what's being done under it ("Syncing saves…", then "Starts once they're done" while a launch waits), and the card's Play button says the same and is disabled. A launch made meanwhile waits in mirad, which answers once the work is done, so the tile goes on to "Launching", whose time starts then. Big screen's launch screen says the same under "Starting <game>", and its two-minute wait for the game to start runs from when the saves work ends.

Big screen's game page has a *Saves* button for an installed game that isn't running. It opens a menu read fresh from mirad, titled with the cloud's state or the backups' summary: *Sync now*, or on a conflict the two sides; *Back up now*; and *Backups (n)*, a list (scrolling with the focus when it's taller than the screen) whose entries each open *Restore* (asking first, since there's no undo note there), *Pin*/*Unpin* and *Delete* (asking). Toasts say how each went. Where the saves are kept, and the saves settings, stay on the desktop's Saves page. While saves work runs, the page's status pill says it in the info color, and *Saves* answers with that toast instead of a menu.

When a scan finds a folder that could be any of several games moved by hand (`library.move_unclear`, and `GET /v1/library/unclear` on every connect), `game/UnclearMoveCard` asks in the same overlay which game it is ("Which game is ~/Games/Copied?", with each game's cover), or *It's a new game*; *Ask again later* leaves it waiting in mirad. `library.move_settled` (settled by another client, or the folder gone) takes the card away, shown or queued.

Two more cards share that overlay (`game/InstallerCards`). `InstallerLeftoverCard` follows `game.installer_leftover`: the folder and its size, *Keep* (the default) or *Delete* (`DELETE /v1/games/{id}/installer`). `ProgramsFoundCard` follows `game.programs_found`: a row per program with its path, a mode (*Runs beside the game* by default) and *Add*, which adds it to the game's launch options. Every such card waits its turn in one queue (`LibraryWindow::QueueCard`) and never covers Settings, a game's card or another card, nor opens unseen.

Jobs answer `202` at once (see [api.md](api.md#jobs)). `client/Jobs` waits for each one's `job.finished` or `job.failed` on the shared event connection, and after a reconnect asks `GET /v1/jobs/{id}` about any it was still waiting on, so the `client/api` calls that start them still hand their caller one result.

### Selection and hover

One click selects a tile. Ctrl, Shift or a drag selects several, and the context menu then offers batch actions; source pages work the same way (`components/TileView`), with *Install (N)* on not-installed titles. There a drag may start anywhere on the page but stays within its section, and selecting in one section clears the other, since the two offer different actions. Double-click launches. A single click never launches, so a misclick can't start a game. *Drag to select* on the Interface tab turns drag selection off.

The game menu's tools open cards over the library. *Run in prefix…* (*Run a program…* for a native or HTML game, which have no prefix) and *Winetricks…* (`game/PrefixCards`) run a program or a verb in the game's prefix, with a rail and a status line while it starts or runs; Winetricks shows common verbs as chips, those already in the prefix (`GET /v1/games/{id}/tricks`) first and ticked, narrowed by its field, which also takes any other verb, and stays open for the next one. *Move to Mira's folders…* (`game/MoveGamesCard`) shows mirad's plan before anything moves: for one game, where its game files and prefix go (from → to, with the size and whether it stays on the same drive) or why they stay; for a selection, a row per game with what moves and its size, which opens (a click, or Right and Left) to the same lines, the games with nothing to move sharing a row per reason, and the total in the footer. A game with a mod manager added has *Remove Vortex…* (or *Remove Mod Organizer 2…*), off while the game runs; its card (`game/RemoveModManagerCard`) opens at once and fills in from mirad: for Vortex how many deployed mod files come out of the game's folder and how many game files it set aside go back, then the size of the manager's mods, downloads and settings that are deleted, with the folders in the label's tooltip. Remove is red and stays off until that's known, and while the manager is open (*Close Vortex first* beside the buttons).

The game menu (`library/GameMenus`) starts with Play or Stop (*Set up…* in its place for a game that isn't set up) and *Update* for a store game, then the download controls, *Play with ▸* and the tool launch options; then *Properties…* (the game's card), *Open game folder* and *Open store page*; *Pin*, *Hide* and *Mark as app*; *Run in prefix…*, *Winetricks…* (only for a game with a prefix), *View log…* and *Open Proton log* (once there is a log); *Move to Mira's folders…*, *Move to emulator ▸* and *Remove Vortex…*; and last *Uninstall…* for a store game, else *Remove…*. Tags and the game's application menu entry are set on its card. The menu for a selection has Pin, Hide, Mark as app, *Tags ▸*, *Application menu ▸*, *Move to Mira's folders… (N)*, and *Uninstall… (N)* when every selected game is from a store, else *Remove… (N)*. Fetching store info and art again is mirad's: it fetches a game anew when what it's found by changes (its name, Steam game ID or SteamGridDB game ID), and every game without a cover once a SteamGridDB key is set or fetching is turned on.

*Store info…* in the game card's panel puts the store's cached info (`GET /v1/games/{id}/metadata`) in the cards' place, as Saves and Achievements do (`game/StoreInfoPage`): an About card (a facts line of release, developers, genres, controller support, achievements and DLC count, the description, chips for reviews, ProtonDB, anti-cheat and content descriptors, and the website), then Screenshots (up to eight, fetched once the page opens; a click opens one large over the page, another click closes it) and System requirements, in a second column when two fit. A game with nothing cached says so. The page reads the info again when a new fetch for the game finishes.

*View log…* is the one tool that keeps a window of its own (`dialogs/LogWindow`, one per log), so it can sit beside the game: frameless, with Mira's bar (the log's name, a Live, Paused or Not running dot, and the window's buttons; `FramelessRoot` gives it the same edge resizing as the main window), a Filter field, Follow, Wrap and Pause toggles, Copy, Save and Clear, and the line count below.

Hovering a tile shows `library/HoverCard` with the name, status, runner, ProtonDB tier, developer and genres. Tooltips everywhere go through `components/ToolTip`, which draws them as the same card.

### Keyboard

`app/KeyBindings` holds every shortcut, and each can be changed in Settings (stored in `shortcut_overrides`). `app/Shortcuts` installs `Ctrl+Q`, `Ctrl+W` and `F1` (list of shortcuts) on both windows. The grid adds `Ctrl+F` search, `Esc`, `Ctrl+1` to `Ctrl+9` filters, `F5`/`Ctrl+R` refresh, `Ctrl+,` settings, Tags and Runners (no keys until given some in Settings), tile size keys and, while the grid has focus, `Enter` to play or stop, `Alt+Enter` for details and `Delete` to remove. That last group is scoped to the grid so the keys still work in the search box. `F1` (and the top bar's keyboard button) opens the list as a card: the window's keys and the common ones as keycaps, grouped under Library, View and Everywhere in two columns, with *Change…* opening Settings on its Shortcuts page. The top bar's ⓘ opens About (`window/AboutCard`), a card with the version (a button copies it with the Qt and system versions, for a bug report), links to the source code, issues and license, who made it, and the service's log.

Everything clickable can be reached from the keyboard. Once focus moves by key, `components/FocusRing` draws an accent ring on the focused control's edge, with a thin backdrop-colored line inside so it shows on an accent-filled row too, kept inside the scroll it's in; a mouse press hides it until the next key. A list marks its current item with its own selection look instead (arrows into a list select the item, as the list's own arrows do), so a game cover never carries two marks. Fusion's dotted focus frame is left out (`theme/Theme`'s style). The arrow keys move focus to the nearest control in that direction (`components/SpatialNav`), first within the page focus is on, then anywhere in the window. They move off a control rather than change it, so passing over a page changes nothing: a button, a radio-style choice (which Qt otherwise leaves out of the Tab order unless checked), a dropdown or a number box's Up and Down, and a slider across its length; Space and Enter press or open it (Enter presses any focused button, not only a dialog's default one). Opening a page leaves focus where it was, such as on the sidebar row that opened it. A list moves through its items first and a text field keeps Left and Right until its cursor is at the end. A page's scroll is never a Tab stop. Tab follows the screen too, not the order widgets were made in: just before it moves, `spatial_nav` relinks the window's Tab chain so each container's controls stay together, in rows top to bottom and left to right, so rows rebuilt later (the sidebar's pinned, recent and source rows, a page's cards) still fall in place. The top bar's tools come after the rest of the window (`spatial_nav::TabLast`), and Tab passes controls under a card. The first arrow after a click starts where the user pointed: it lands on the control clicked (or the one now at that spot) when the click left focus elsewhere, as a sidebar row that opens a page does, and from a click on nothing it moves from that spot. Big screen marks focus its own way and keeps its own arrows.

A controller works in the desktop windows too (`app/DesktopController`), through the same focus and keys: the stick and d-pad move focus as the arrows do (a horizontal press steps a slider or spin box), A presses the focused button or sends `Enter`, B sends `Esc`, X or Start (Menu) opens the focused control's right-click menu (a list's at its current item), Y sends `Ctrl+F`, the shoulders are `Shift+Tab` and `Tab`, the triggers `Page Up` and `Page Down`, and a tap of Guide opens big screen once let go, so the press isn't still down as it opens (held over 1.5 s, as many controllers are to turn off, it does nothing). A control under a card can't be reached. It opens the controllers (`bigscreen/GamepadInput`) on a worker thread at launch, since that takes SDL about 50 ms that would otherwise hold up the window's first paint, and reads them only while a Mira window is in front and big screen is closed, and a button still held when Mira comes back to the front counts only once released. It uses big screen's controller settings (which button selects, stick sensitivity, scroll speed).

Quit goes through `QApplication::closeAllWindows()` so `LibraryWindow::closeEvent` saves its prefs.

## Theming

`theme/Theme` sets the Fusion style, palette and stylesheet at startup instead of inheriting the desktop's.

A theme is a TOML file of tokens. `themes/base.qss` is the only stylesheet, and every `@token` in it is filled from the current theme. `mira-dark` and `mira-light` are built in; user themes go in `$XDG_CONFIG_HOME/mira/themes/*.toml`. On start, Mira writes `mira-dark.toml` and `mira-light.toml` there if they're missing, to edit or copy. A user file with a built-in theme's name applies over it key by key, so a key the file doesn't set (such as one a later version adds) keeps its built-in value. Missing or invalid keys fall back to the defaults. A theme with `system_colors = true` (both built-in ones) takes the desktop's colors from two places. Its window, panel, text and accent colors come from the desktop's palette where Qt's platform theme reads one (on KDE, the color scheme in `kdeglobals`, even without the Plasma plugin; on GNOME, Cinnamon, MATE and Xfce, the GTK theme through Qt's GTK platform theme, which the AppImage and packages ship and run against the system's GTK and GLib); from a desktop of the other brightness only the accent is taken. On any desktop with xdg-desktop-portal's appearance settings (GNOME 47 and later, Plasma 6, Cinnamon and others), `theme/DesktopPortal` reads the accent color, which wins over the palette's, before the first window, waiting at most 250 ms, and follows its changes. Where neither has anything, the file's colors stay. Status colors and `accent_hidden` are always the theme's. The palette is read again when the desktop's theme changes. The `theme` pref is a theme name or `auto`, which follows the desktop's light/dark setting (Qt's, or the portal's `color-scheme` where Qt doesn't know it). It needs Qt 6.10 or later on GTK desktops: older Qt reads the portal's "no preference" as light, so a dark GTK theme on Cinnamon came out light.

File and folder pickers are the desktop's own, through xdg-desktop-portal: unless `QT_QPA_PLATFORMTHEME` is set, `main.cpp` starts Qt with its portal platform theme (`xdgdesktopportal`, bundled in the AppImage next to the GTK one), which only takes over the file dialog and keeps the desktop's usual platform theme for the palette and fonts. It's unset again once the app starts, so mirad and games don't inherit it. Without a running portal Qt falls back to that theme's picker.

A card over a game's art (the game card's) is the surface color at the theme's `art_card_alpha` (255 makes it solid), as the dim behind a modal card is `modal_scrim_alpha`.

`theme::Overrides` applies tile spacing, grid padding and corner radii from `frontend.toml` on top of any theme. A key left out of the file uses the theme's value.

Widgets that paint by hand read tokens directly and repaint on `theme::Notifier::Changed`: `library/GameTileDelegate`, `library/CoverArt` and `game/HeroBackdrop`.

Widgets don't set colors themselves. They set a style property and `base.qss` styles it: a label's look is a `TextStyle` (`components/Text`: its role, size and tone as separate axes, with presets such as `text::kDetail` and `text::kError`) set through `SetTextStyle`, and other properties go through `theme::SetStyleProperty`; both re-polish after a change. Counts, sizes and paths are written by `components/Format` (`Counted(3, "game")`, `SizeText`, `HomeRelative`), so every label says them alike. A button's look is its kind (`components/Button`: Primary for the action a card or step is for, Danger for one that deletes, Link and Text for quiet actions, Glass over a game's art; a plain `QPushButton` is Secondary), each styled at rest, hover, pressed and disabled. Which button Enter presses (`setDefault`) is separate from its look, so a default Keep or Cancel stays plain. A frameless glyph button is an `IconButton`, whose tooltip is also its accessible name. A filter, choice or tag is a `Chip` (a pill: surface fill and border, solid accent with on-accent text while on, with an optional icon, muted count, dropdown chevron or × (Delete and Backspace remove it too); a folder tag adds an accent outline; a rating chip has a color of its own, `SetTint`, tinted with it while off and filled with it while on), a row of toggles from a list setting's choices is a `ChipGroup`, and a label beside a name ("Beta", "Default", a review or ProtonDB rating) is an outlined `Badge` in its tone, or in a color of its own (a ProtonDB tier's, a Steam review group's), lightened or darkened by `InkFor` so it reads on either theme. Both are painted, with a corner of `min(height / 2, radius_control × height / 12)`: full pills at the default rounding, square at 0. Their sizes come from the text size, and colors from the theme as it changes. The shapes themselves live in `components/paint/` (QPainter only, colors and sizes passed in), which big screen draws its pills and progress rails with too. A state is a `StatusLine`, its `Dot` painted in the state's tone, and a link inside text is an `Anchor`, in the palette's link color. `theme/Icons` draws icons as vector paths in the theme's text color.

## Layers

```
client/      talks to mirad, draws nothing
theme/       the theme tokens, stylesheet and icons
components/  the component library: the cards, rows, controls, popups and layout pieces every screen is built from, knowing nothing about games
app/         process-wide services: notifications, error help, shortcuts, the desktop controller, tray, starting mirad
library/     the library model, the library page and how a game is drawn: tiles, covers, hover card, game menus and actions
game/        a game's card: its edit form, tags, overrides, art picker, achievements, saves and installer cards
sidebar/     the sidebar: nav rows, source rows, pinned and recently played rows and their style card
sources/     the source list, source pages with their setup and settings cards, removing a source, and Manage sources
runners/     the Runners page
tags/        the Tags page and its game picker
activity/    the download and job tracker and the Activity panel
updates/     the update check, Mira's own update and the Updates panel
downloads/   link downloads: the queue's model, the password popup and the Downloads window
settings/    the Settings screen: its nav, pages and the editors that turn mirad's schema into rows
window/      the main window, its top bar and About
dialogs/     modal dialogs
```

`client/` and `theme/` depend on nothing else here, and `components/` only on `theme/`. The feature folders use those and each other, and `window/` puts them together. `components/` and `theme/` build as a library of their own (`mira_gui_components`), which mira-gui and the GUI tests link; `mira_gui_components_check` links all of it alone, so a component that calls into feature code fails the build.

### Components

Each kind of thing the GUI shows more than once is one component with one API and one look; a screen is built from them, and something a second screen needs becomes a component rather than a copy. A component takes its colors from the theme (through the stylesheet or at paint time) and its sizes from the text size and `Metrics`, never as literals of its own, so it follows the user's theme, rounding and text size as they change.

| Kind | Components |
|---|---|
| Cards | `Card` (a titled group of rows, foldable, scrollable, translucent over a game's art), `SheetCard` (a card that stands alone: heading, close kept last, back arrow, error line, button row), `SettingRow` and `ExpanderRow`, `DividedRows`, `Fold`, `SettingsPage`, `ChangeBar`, `PageHeader`, `ListRow` (a divided row of a popover's list) |
| Text | `Text` (`TextStyle` and `SetTextStyle`, `Anchor` for a link in text), `Labels` (`MakeLabel`, `ElidedLabel`, dividers), `Format` (counts, sizes, paths), `Dot` and `StatusLine` (a state with its dot), `Badge` |
| Buttons | `Button` (by kind), `IconButton`, `NavRow` (the sidebar's and Settings' rows), `Chip` and `ChipGroup`, `Segmented`, `Switch`, `LaidOutButton`, `UnclippedLabelButton` (a checked segment or tab's semibold label may use its padding), `TabRow` |
| Fields | `SearchField` (and `AddClearButton`), `FlatCombo`, `PathField`, `CopyField`, `ListEdit`, `ShortcutEdit`; a number box is a `QSpinBox` at `kNumberWidth` |
| Popups and windows | `PopupDialog`, `Popover` (placed by `popup::PlaceBelow`, again when it resizes while open), `PopupCard`, `HoverDwell`, `ToolTip`, `WindowCards`, `ModalOverlay` (dimmed by the theme's `modal_scrim_alpha`), `TitleBar` and `WindowButtons` (`WindowChrome`), `FramelessRoot` |
| Layout and input | `Metrics` (`kControlHeight`, `kRowPaddingX`, `kLabelInset`, the field width, `kCardColumn` and `ColumnsWidth`), `ColumnGrid` (cards in fixed-width columns, each at its own height, starting at the left of the widest grid that fits: flowed down one column and on into the next, or placed by the page per column count), `SectionNav` (buttons that glide a scroll to their section and follow it), `Scrolling` (`SetUpScrolling`, `SettleLayout`, `SeeThrough`), `OverlayScrollBar`, `FlowLayout`, `TileGridLayout`, `TileFit`, `TileView`, `FocusRing`, `SpatialNav`, `ProgressRail` |
| Painting | `paint/Pill` and `paint/Rail`, shared with big screen |

Big screen draws its own controls for a TV and a controller and shares only `components/paint/` with the desktop UI.

| `client/` file | Role |
|---|---|
| `Transport` | One socket round trip: timeouts and the error envelope. |
| `JsonMapping` | JSON to and from the structs in `Types.h`. |
| `Async` | Runs a call on a worker thread and delivers the result on the main thread. |
| `api/` | One function per endpoint, in `namespace api`, one file per area: `Games`, `Library`, `Config`, `Artwork`, `Runners`, `Stores`. `Request` holds what they share: `ReadReply` turns a reply into a result, checking the body's shape and catching a field of the wrong type, and `RunJob` waits on a job. |
| `Jobs` | Waits for a job's `job.finished` or `job.failed`. |
| `EventStream` | The `GET /v1/events` connection, reconnecting with `Last-Event-ID`. |
| `EventHub` | Shares one event connection between every window. |
| `Events` | Parses each event's payload (`events::ParseGameState` and so on). |
| `Types.h` | Plain data the UI depends on. |

`async::Deliver` posts results to `qApp` and checks a `QPointer` to the requesting widget on the main thread. Posting to the widget itself would read a possibly deleted object on the worker thread.

`LibraryWindow` fetches the whole library once into `library/GameLibraryModel`, and `library/LibraryPage` filters it on the client, which keeps search instant and makes "Playing now" and "Never played" possible. Events then patch the view directly. There is no polling.

A search also looks through the games you own but haven't installed. `library/OwnedTitles` fetches every store's titles (`GET /v1/library`) in the background as soon as it connects (mirad answers from its stored lists), again when a typed search finds the list more than ten minutes old, and after a store install finishes. Matches (`MatchOwned`, one per game across stores by name) show under the library's own in a *Not installed* section with an Install button; a game owned on several stores asks which copy to install. While that section shows, the grid sizes to its tiles and the page scrolls as one. Their covers are fetched only for titles a search showed. `OwnedTitles` also lists again whenever mirad reports a store's list changed (`library.catalog_checked` with `changed`).

The tab row's last tab, *Not installed* (with its count), isn't a filter of the library: it puts every store's titles that aren't installed (`GroupOwned`, in the stores' order) in place of the grid, asks mirad for them again on opening, and swaps the filter pill for `library/TitleFilterBar`: Store, ProtonDB and Steam reviews dropdowns that each pick any number of values (a title passes when any of its copies' stores is picked), the sort (store order, name, best reviewed, best on ProtonDB) and *Clear filters*. Its tiles and a search's store matches read "<Store> · NN%" on the status line, with the ProtonDB pill; covers are fetched for the titles it shows. Picking a filter tab, or Ctrl+1…9, leaves it.

Only `game.added` and `game.updated` carry a game record, so views check the event type before parsing one. `game.state` carries only the state and launch details, so an exit triggers a re-fetch. A game handed to Steam or a launcher reports `tracked` in the launch reply and `game.launched`, and isn't marked running unless it is tracked.

## Game card

*Properties…* opens a card centered on the whole window, everything behind it dimmed, the sidebar included (`game/GameCard`): a panel on the left, then the game's settings in two 516 px columns of cards (`components/ColumnGrid`), as wide as those need (at most the window's width less a margin) and 88% of the window's height. On a smaller window (1366 px) the panel is 268 px instead of 340 and the columns 468; when even those don't fit, the cards take one column, and a card under 860 px tall leaves the cover out. The game's art fills the whole card behind both (`CardBackdrop` in `game/HeroBackdrop`): its blurred cover as a dimmed wash, the hero art sharp at the top left behind the panel and fading out into it, and a scrim that darkens toward the bottom; the cards over it are translucent (`Card::SetOverArt`), and Close sits at the top right as a glass button. The panel (`game/GamePanel`) holds the cover, the name, the status and source on one line and the play time on the next, Play (with a button per tool launch option under it), *Store info…* and *Change art…* side by side (one above the other when both labels don't fit), the saves line and the achievements line, a divider, then its lower part: a jump list of the cards under two headings, *How it runs* and *The game*, which glides the cards to the one clicked and follows their scroll (`components/SectionNav`), each row noting how many settings its card sets for the game ("2 set"). A row hides with its card, and a heading with all of its rows. Opening Saves, Achievements, *Store info…* or *Change art* puts that page in the cards' place and its controls in the panel's lower part under Back and the page's title (*Back up now* and the cloud's state; the unlocked count with its rail; the four art slots two by two (`components/TabGrid`), chips and *Choose image…*); Back or Esc returns to the cards and the jump list, while the panel's top stays put. `game/GameEditForm` builds the cards from the same rows as Settings, by the kind of game (`game/CardColumns`, one list per column, the one place to change the order): the left column is how it runs (for a Steam game a Steam card with its Steam settings, launch options and environment variables, then Proton; for an emulator's game an Emulator card with the emulator, picking another moves the game to it, its arguments and environment variables; for any other a Runner card, an HTML game's runner picker listing only browsers and every other game's leaving them out, and its store's card, Epic or GOG, when it has settings there), then Display, Performance and overlay, and Stopping and logs; the right column is the game itself (Details with name and tags, Game detection with what Mira takes it for, its Steam game ID, its SteamGridDB game ID and its entry in the save locations list, then for a game that is neither Steam's nor an emulator's a Launch card with its executable, arguments, working folder, launch options and environment variables, then Files, Scripts, Saves, Menu entries). A card for a group those lists don't name goes at the end of the right column and its jump list. Files holds the Game folder and the Prefix folder (an HTML game's has no prefix row, since its data folder is its browser profile; an emulator's shows the game file), each read-only with Open and *Change…*, which points the game or its prefix at the folder (or file) it was moved to, saving at once and moving nothing (`PATCH /v1/games/{id}` with `install_path` or `data_dir`). A game whose store or launcher keeps track of its files (`files_kept_by`) has no *Change…* for its folder. A missing game's card starts with a line saying where its files were and *Change folder…*. Scripts has the game's pre-launch and post-exit scripts with their ready-made steps inside each script's row (shown only when the game can use them); that row's undo covers the script and its steps together, so clearing a script clears its steps too. A card with no rows for the game is left out. Launch options (`game/LaunchOptionsEdit`) are rows of their own under their row, which holds *Add…*, as a list setting's items are, then *Play starts* (the game's own program or an option that starts it, a flat dropdown) and *Don't ask which to start* (a switch, only with an option picked), each with its own dot and undo. Tags show as chips (`game/TagEdit`), always in the library's tag order (`TagOrder`, the Tags page's: folder tags in their order, then by how many games have each), whatever order the game stores; the filter's Tags list and the menus' *Tags* follow it too. In a library folder sorted by tag, the game's folder tag (its pick, `folder_tag`, else its first tag in the record's `folder_tags` order) is outlined with a folder icon; a store game, which never moves, gets no mark. Its other folder tags carry a muted folder icon; a click on one, or its menu's *Use as this game's folder*, picks it for this game (no pick when the order gives it anyway), and the folder chip's *Follow the folder tags' order* drops the pick. A click on any other chip does nothing, so a click only ever means a folder pick. The pick saves with the tags in one `PATCH /v1/games`. Which tags are folder tags, and their order, is set on the Tags page only. The room the change bar needs under the last card stays once added, so a card scrolled to the bottom never jumps as the bar hides. The library menus' *Tags* lists every tag in the library for the game or the selection (a partly shared one as "RPG (2 of 5)", adding it to the rest; a fully shared one checked, taking it off) with a field for a new one. The folder tags of the games' library folders come first under a *Folders* heading row (a disabled row, since Fusion draws a checked action's icon in place of its tick and a menu section's text not at all). The game's own settings (`game/OverridesEditor`, from `GET /v1/games/{id}/config`) show only those the game can use (`applies`), each in the card for its schema group (the same groups as Settings' cards): a store's settings in that store's card, Environment in the Steam, Emulator or Launch card, Proton in Runner, the save groups in Saves, and every other group in a card of its own. A row the game sets for itself has an undo button (*Use Settings' value*) but no dot, which marks only edits not saved yet; its undo first drops an unsaved edit, then puts the row back on Settings' value, which saves as a cleared override. Environment variables (`launch.env`) are one list: while the game takes Settings' list it shows muted under *From Settings* with *Edit…*, which gives the game a copy of its own, and undo goes back to Settings' list. Steam's card shows the list only while the game launches directly, since Steam doesn't pass it on otherwise. Runner options are an expander in the Runner card, one row per key of the picked runner's `GET /v1/runners/{kind}/schema` (for "Default runner", the kind of the record's `default_runner`), titled by the kind and hidden when it has none; they save as a merge patch of the keys that changed, a cleared one as null. The change bar counts unsaved edits from all of them and saves them through `PATCH /v1/games/{id}`, `PATCH /v1/games` for tags and `PATCH .../config`. The card stays open after a save, and reloads on `config.changed` so the rows taken from Settings follow it.

A game with achievements has a line in the panel under the saves line, "48 of 52 achievements" with a trophy, a flat row that lights up on hover; the two lines' room is kept while there's nothing to show. When the store has none for the game the line says so, muted and not clickable ("No achievements on Epic Games"); a game no store reads them for has no line. The card shows what mirad has cached at once and asks for a refresh in the background when there's nothing cached yet or it's over a day old; `game.achievements_ready` (after a session, say) updates it while open, and turning *Show achievements* off hides the line and the page at once. These refreshes stay out of Activity, and a failed one leaves what was cached, with no notice. The line opens `game/AchievementsPage` in the cards' place (the panel's Back and Esc return), with the count and the progress rail in the panel, then a tile per achievement in the store's order, as many columns as fit, each with its icon (dimmed while locked), name, description, unlock date or *Locked*, and rarity, under 10% in the warning color. A hidden one that's still locked shows as *Hidden achievement* with a lock, and its picture isn't loaded, until it's clicked. Icons load through `GET .../achievements/icon` four at a time, in the page's order, as it opens and go when the card closes.

Above it sits the saves line, its two parts at either end, or the second under the first when they don't fit on one line: "3 backups · last after today's session", or what stands in for backups ("No saves yet", "Saves kept by Steam Cloud", "Save locations not known"). A cloud conflict or a failed last backup is what the line says instead, in the warning color. It reloads on `game.saves_changed`, `saves.manifest_changed` and changes to the `saves.*` settings, and drops an answer that a newer load overtook. The line opens `game/SavesPage` in the cards' place, as achievements do, with *Back up now* and the cloud's state (a dot, when it last synced and *Sync now*) in the panel. Its cards sit in two columns when there's room: *Backups* on the left (newest first and tinted, each with when, why and its size, a pin toggle that keeps it whatever `saves.keep` says, and *Restore* and *Delete*), then *Where they are* (each folder, a prefix's user folder shortened to "prefix ›" and the home folder to "~"; one the user added has *Remove*; then *Add a folder…*, a folder picker starting in the game's prefix or folder, and *Open prefix* or *Open game folder* in the file manager), *Which saves to keep* (only on a cloud conflict: the two choices of the launch card, as upload and download) and *Settings* on the right. Adding or removing a folder goes through `POST .../saves/folders`, so mirad escapes the path, writes it against the game's folders (`<base>/…`, `<prefix>/…`) and changes the list in one step. Restoring doesn't ask, since mirad backs up first: a note offers *Undo* (restoring that backup). Deleting a backup asks. A sync from the page that finds a conflict shows its choices on the page with no notification. *Settings* shows the game's `saves.*` values, and each goes back to the cards and scrolls to that row in the Saves card rather than editing here. While mirad works on the saves (`doing` in the answer, then `game.saves_activity`), *Back up now* says what it's doing, the cloud's state in the panel says it too, and the page's actions wait; focus moves off a button before it's disabled, so the page doesn't scroll to the next one.

## Settings

Settings takes over the window body, its nav column in the sidebar's place: the sidebar's current width (plus the splitter handle, so the divider doesn't move), its margins, row height and color, and its back row as tall as the sidebar's first row. `settings/SettingsNav` lists the categories under three headings (Look and feel, Games, System), each with an icon, and shows every category's page of cards (`components/Card`) one after another in a single scroll. Clicking a category scrolls to its page, the list follows the scroll, and the current page's group heading and title stick to the top, over the page's cards at their width (`components/SectionNav` does the jumping and following); the last page gets room below it so it can reach the top too. A page lays its cards in as many 516 px columns as fit, up to three (three on a 1920 px window, two at 1366), with its title over the grid's left edge; a page with fewer cards than columns starts where a full page's first column does, so every page's left edge lines up, 20 px between columns and 16 px between cards (`components/ColumnGrid`). Cards flow down the first column and on into the next, split where the heights balance; the split holds while a card folds or unfolds and is made again once the values have loaded. Interface places its cards itself, Library and Layout (each with its preview) apart from the tall Appearance card. While searching, a page uses no more columns than it has matching cards. The column grows with a larger text size, and a long label wraps to a second line rather than being cut short. Every row is as tall whatever its control, and a card's title starts where its rows' labels do, as do its lists' items, inside the card's border; a sunken row that ends a card takes its bottom corners. Text fields share one width and number boxes another, so their edges line up; a field with buttons beside it (Browse…, Open, Change…) takes a line of its own under its label, as does a segmented control whose options don't fit beside it; a flat dropdown (`components/FlatCombo`) is as wide as its value, and its open list as wide as its longest option. Every non-editable dropdown in a card (`PopupDialog`'s too) is a `FlatCombo`: the card's stylesheet drops a dropdown's frame and padding, which a plain `QComboBox` doesn't size for, so it cuts its value short. All text is one size (`theme::TextPoints`): *Text size* in Appearance, else the desktop's, else 10 pt when the desktop gives none in points. It applies on save without a restart; the stylesheet's pixel sizes (small text, headings), picked at 11 pt, scale with it, as do sizes in code through `theme::TextPx`. Only game titles on covers keep the desktop's size, since their slot on a tile is a fixed height; they grow with the covers. `KeepTextSize` keeps every widget class on it when the desktop's platform theme sets per-widget fonts, checking again on a theme, palette or font change and whenever a window shows, and restyles when the desktop's size changes while the text follows it. A card's rows can be expanders: a row with a name, a muted note (an emulator's consoles), a summary on the right ("Installed", "As in Settings") and a chevron, opening to indented rows on a sunken surface. Stores, emulators and downloads are expanders (the schema's `item`), emulators grouped in a folding card per maker with "N emulators · M installed" in its header. A choice of two or three is a segmented control (`components/Segmented`, the one used everywhere: Sources, Runners, Set up Mira) and a longer one a flat dropdown, both showing the schema's `option_labels`; a value the dropdown doesn't list (set by hand, or a runner since removed) is added as it was set, so saving keeps it (`SelectOrKeep`); a number shows its `unit` inside the box. A list's items are rows of their own under it, each edited in place with a remove button, and a list longer than 6 shows its first 3 and *Show all N*. In the scroll, the wheel never changes a dropdown, number box or slider, focused or not; it scrolls the page past them. Scroll bars take no room: `components/OverlayScrollBar` draws each as a 4 px thumb over the content, shown while it scrolls, for a second after and while the pointer is on the thumb, which drags (not when a page opens under the pointer); Qt's own bar stays, 1 px and undrawn, holding the position. Every page that scrolls (Settings, a source page, Runners, a game's card, Activity, the sidebar) goes through `components/Scrolling`: a wheel notch moves about 120 px, and Page Up/Down and Home/End scroll the page wherever focus is in it, the nav column included, except in a number box or text area. Anywhere in the app, a mouse wheel's notch glides its scroll area over 200 ms to where it would have jumped, and notches during a glide add up (`SetUpSmoothWheel`, on each area's vertical bar, so the view still sees the wheel first: Ctrl still zooms); a touchpad's own pixel steps, and lists that scroll by items or lines, are left as they are. A touchpad is told by its scroll phases or a system-synthesized source; on Wayland only those count, since a mouse wheel sends a pixel delta too and Qt gives every pointer event the seat's one device, named "touchpad" once the compositor offers gestures. Elsewhere a touchpad device type or a pixel delta also counts. Every screen that edits settings is built from the same pieces: a titled card, rows with the label on the left and the control on the right (a switch for on/off), and a line between rows. A row's doc is its label's tooltip, shown after 0.3 s of hover. While a row has a change that isn't saved yet, a dot marks it and an undo button puts back the saved value. Cards whose settings make sense to reset together (Layout, the Shortcuts cards, and schema groups with `group_resettable`) get a "Reset to defaults" button in their header while anything in them differs from its default; like any edit, it applies on Save. Nothing applies until saved: the change bar at the bottom counts the changes and saves or discards them, and Back asks first if anything is unsaved. A setting saved elsewhere while Settings is open (the CLI, a source page, another client, through `config.changed`) shows at once; a row with an unsaved edit keeps the edit, and Discard then puts back the newly saved value. A setting put back to its default is removed from `settings.toml` (`POST /v1/config/reset`) rather than written out.

- **`settings.toml`** holds backend settings. Their pages are generated from `GET /v1/config/schema`: categories, order, labels, card titles (`group_label`), folded cards (`group_collapsed`), card resets (`group_resettable`), runner pickers (`is_runner_ref`, showing a listed runner by name and storing its reference, and listing builds again when one is installed or removed, from `EventHub::RunnersChanged`; `runner_kinds` narrows one to those kinds, with Auto only when it's the default, as for the browser HTML games open in), folder and file pickers (`path`), lists for arrays (`components/ListEdit`) and toggle chips for an array picked from `choices` (`components/ChipGroup`) all come from the schema, so a new backend setting needs no frontend change. A setting marked `config_only` (an expert or derived one, set in `settings.toml` or the CLI) is left out of every page and a game's card. The Sources page lists every store and launcher as an expander of its settings, marked Store or Launcher; a source that isn't added yet shows only the rows that add it. Each row's editor comes from `settings/SettingEditor`, which a game's own settings (`game/OverridesEditor`) and the source settings card share. A secret's field is masked and never holds the saved value, which mirad doesn't send (`secrets_set` marks it `kSecretSaved`): it reads *Saved* or *Not set*, typing replaces the key, and a clear button inside it removes a saved one. A `link` is a button beside it. The two display settings ask `GET /v1/display`: Resolution is a list of the primary monitor's modes after Unchanged, and HDR notes when the monitor can't do it (and is greyed out while off) or the desktop isn't Plasma on Wayland. A setting with `shown_in` gets no row of its own: its chips sit inside that setting's row, over its text line in one box (`SettingEditor::Embed`), so the pre-launch and post-exit scripts each show their ready-made steps above the user's own commands. Its changes and overrides mark the host row, the host's undo reverts both, and search finds the host by either. Settings with a `paired_key` are paired (`PairChoices`): turning a pre-launch step on or off does the same to its post-exit pair, which can then be changed alone, and a choice with `needs_pair` is greyed out while its pair is off. The schema's Tags category is left out: the Tags page shows those settings. Search (`settings/SettingsSearch`) matches every typed word in any order against the key, label, category, card title, doc and `keywords`, and opens a folded card that matches. It filters the scroll in place: pages with no match hide and dim in the list, and the rest show their match count.
- **Interface and Shortcuts** are the GUI's own pages. Themes are picked from tiles that draw a small window in each theme's colors (`settings/AppearancePreviews`, `theme::Peek`); the tile toggles sit under two of the user's games drawn by the grid's own `GameTileDelegate`; the layout sliders reshape a strip of covers before anything is saved. Interface's Sidebar card holds the same rows as the in-window Pinned and recently played card (`sidebar/SidebarStyleCard`); the sources' sidebar switches are on the Sources page. Shortcuts are keycaps (`components/ShortcutEdit`): click one and press the new keys, Esc cancels and Backspace leaves none.
- **`frontend.toml`** holds GUI state and preferences (`FrontendPrefs` in `client/Types.h`), read and written as the `frontend` key of `/v1/config`. The backend never validates it.

## Notifications

`app/Notify` handles every message. Failures (`Failed`, `FailedWithHint`, `FailedWithAction`, `Warn`) are persistent desktop notifications; confirmations (`Notice`) use the desktop's default timeout. Only questions (`Confirm`, `LeaveUnsaved`) and answers to a button (`Info`) are popups. Pages with their own status line, such as `RunnersPage` and `ArtPickerPanel`, report errors there.

A popup (`components/PopupDialog`) is the same card as the window's other cards, laid over the window it was asked from with the rest dimmed: a level icon before the title, the message under it, and the buttons on the right, Cancel first and the action last. A destructive action is red and Cancel keeps the focus, so a stray Return never picks it. A click beside the card is a no. Asked while the window is hidden or minimized, it's a frameless window of its own. Other cards go through `components/WindowCards`: `cards::Show` puts a card in the library window's card overlay (`LibraryWindow` is a `CardHost`, so the sidebar stays bright beside it), or over any other window with that window dimmed; Esc or a click beside it closes it.

Success that already shows on screen gets no message. A notice only goes out when nothing in the window would change, such as "No new Steam games found."

Notifications use `org.freedesktop.Notifications` (`app/SystemNotifier`) with a `desktop-entry` hint of `mira`. `FailedWithAction` adds a button that raises the window and runs the action. When the service doesn't take one (none running, or rate-limiting Mira), a failure, warning or warning-level notice becomes a row in Activity (`notify::SetFallback`, set by `LibraryWindow`), so it never interrupts; before that window exists it's a popup. Other notices are dropped.

Messages are plain text, since `mirad`'s errors quote paths and commands. Failures show `mirad`'s message under a sentence naming what failed.

Every request result carries an `ApiError`: `mirad`'s message, code, `hint` and `fix` (see the error envelope in [`api.md`](api.md)). `notify::FailedRequest` shows the hint under the message and turns the fix into a button through `app/ErrorHelp`: the setting to fill in, the Runners page, the game's settings or log, running its installer with the window shown, or the store's page. What to say and where to point is `mirad`'s knowledge, so a new error needs no frontend change. The one case `ErrorHelp` words itself is `mirad_unreachable`, set by the transport when a request never reaches `mirad`, which gets a *Start mirad* button. Status lines use `error_help::Describe` for the same text inline. Failure events carry the same fields, so an Activity row for a failed install or download shows the hint and a button for the fix. `LibraryWindow` registers the routes with `error_help::SetNavigator`.

A `crashed` `game.state` gets a failure with a *View log* button, titled by its `code`: "couldn't start", "was killed" or "crashed". `mirad` only reports one for a real crash, so a game that exits non-zero on a normal quit stays quiet.

On connect, `mirad` replays its event buffer and then sends `stream.live`. Windows apply replayed events but only announce (notifications, install results, crashes) what comes after it, so a restart doesn't repeat old messages.

## Cover art

`library/ArtworkStore` fetches art from `GET /v1/games/{id}/artwork` and always returns a pixmap:

- A game's record says which art it has (`art`, see [api.md](api.md)). A game without a cover is never asked for one; `library/CoverArt` draws a placeholder with a hue from the game's id, so it stays the same across restarts.
- A cover is fetched once, and again only when its version changes in a record, `game.metadata_ready` or `game.artwork_selected`. The old image stays on screen until the new one lands.
- At most eight requests are in flight.
- A small copy of every image is kept; covers are kept as drawn at the tile width in use and fetched again for a new one. While a zoom moves (`library/ZoomSettle`, one per page and the Tags picker), covers are scaled quickly from the last copy and not kept; the covers on screen are fetched at the width it's heading to, and once it stops every other width that view kept is dropped. The sidebar's covers keep their size through any zoom, so they're never drawn quickly and never dropped to make room. Quick scaling is the whole app's, so once a zoom stops every cover drawn quickly meanwhile is announced as changed (`CoverChanged`), and a view that didn't zoom (the Tags picker while hidden mode switches the grid's size) draws it again; a view closed mid-zoom ends its quick scaling.
- Closing the window hides it to the tray, unless *Keep Mira in the tray when its window closes* (`close_to_tray`) is off: then closing quits as the tray's Quit does. Hiding to the tray drops every image, small copies included, and closes the open page (unless it has unsaved edits); the window comes back on the library and fetches covers again as they're drawn. mira-gui runs with one malloc arena (`main.cpp`), since images freed in the worker threads' arenas stayed resident.

Without `steamgriddb.api_key`, non-Steam games may have no source. `mirad` then fails the fetch with `no_steamgriddb_key`, and the GUI says so once per session: a popup offering Settings when the user asked, a notice after a background scan.

Metadata is fetched when a game is first added, and again by mirad as the game menu's paragraph says. Refresh the library (F5) fetches art for every game still missing it.

`game/ArtPickerPanel` is the game card's *Change art*, with Covers, Hero art, Logos and Icons tabs, each counted as the picker opens (the art mirad has plus SteamGridDB's total, from one first-page request per tab). It shows a slot's candidates as a grid of previews, one page of SteamGridDB's list at a time as the grid scrolls, with placeholders for the rest so the grid is its whole length from the first page on. Under the slot tabs, a row of style chips and an *Adult* chip (only what SteamGridDB marks adult, shown when there is any) appears with that first page, counted by SteamGridDB itself (`styles` and `adult`); a chip asks SteamGridDB for its pages of that style or adult art only, while a chip for art from elsewhere (Steam's) just narrows what's loaded. The row keeps its height while empty, and wraps when there are more chips than fit. The grid keeps its previews decoded at about the size of its cells, and only the pick at full size for the card. The grid leads with the user's own image when the slot uses one (*Yours*) and *None*, which leaves the placeholder and stays through refreshes (`DELETE .../artwork`). *Choose image…*, *From URL…* (downloaded by the GUI, http or https, up to 32 MB) and dropping a file or link add a new *Yours*. `mirad` downloads the previews (`POST .../artwork/thumbs`) only for what is on screen plus one screen ahead, and deletes them when the GUI quits. Clicking a preview shows it on the card and in the change bar; *Use this cover* (or hero) applies it and keeps the picker open, and *Cancel* goes back to the one in use. A pick stays, and stays shown on the card, while another tab is open; with picks on several tabs the bar reads *New cover and hero art picked* and *Use these* applies them all, while *Cancel* or closing the picker drops them all. The *Art from* menu picks which SteamGridDB game the art comes from. A not-installed title's *Change cover…* (on the library's and source pages' Not installed tiles) opens a game card for the title (`GameCard`'s title constructor): its name and store, and the same picker, covers only, for the id the title will have once installed, with Back closing it.

## Running against a dev daemon

Run a separate daemon on its own socket and point the GUI at it:

```sh
XDG_CONFIG_HOME=~/.mira-dev mirad --socket ~/.mira-dev/mirad.sock &
MIRA_SOCKET=~/.mira-dev/mirad.sock build/dev/frontend/mira-gui
```

`XDG_CONFIG_HOME` only separates config, not the socket, so without `--socket` the dev daemon would take over the default one. The window footer shows which socket is in use.
